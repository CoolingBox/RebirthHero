# 《轮回大侠》战斗特效设计 v0.2

> 2026-11-14 · 取代 v0.1 的"命中点几何"思路，改为**三段式攻击 + 相性差异化**
> 起因（实测反馈）：① 看不出谁打谁 ② 武学没个性 ③ 受击"随便画个线"太敷衍

---

## 0. v0.1 落地后暴露的问题

v0.1 已实现斩线 / 内功环 / 真伤裂 / 火花 / 死亡碎片 / 毒泡 / 火星 / 闪避弧。
问题不在数量不够，在**信息结构**：

| 问题 | 根因（代码事实） |
|---|---|
| 看不出谁打谁 | `PlayHitFx` 把斩线截到目标身前 120px，刻意不连攻击者。方向感被这个妥协丢掉了 |
| 武学没个性 | 特效只按 `DamageKind` 分三色（外功橙 / 内功青 / 真伤紫）。`Category` 有 13 种相性，一个都没用 |
| 受击太敷衍 | 命中只是一根线 + 几条射线，没有形状层次，剑和刀、掌和拳看上去是同一件事 |
| 没有"释放" | 所有特效都以目标为圆心，释放者自始至终无视觉变化。攻击只有"落"，没有"起"和"飞" |

**核心判断**：v0.1 解决的是"目标身上发生了什么"，没解决"**谁、用什么、怎么打过来的**"。

## 1. 三段式攻击模型

每一次攻击拆成三拍，**缺一不可读**：

```
起（释放者）        飞（轨迹）              落（目标）
0.06~0.08s         0.12~0.30s             0.16~0.32s
相性色一闪    →     相性投射物飞过去   →     相性命中形爆开
```

- **起**：释放者卡面中心一小团相性色亮起即收，告诉玩家"是这个人出手了"。不做大动作，频次太高会吵。
- **飞**：投射物从释放者锚点飞到目标锚点。**这是 v0.2 的核心增量**。
- **落**：命中形在目标处展开，**每种相性一种形状**，不再共用一根线。

**投射物消亡时自动带出命中形**（由特效层在 `_Process` 里联动），
调用方只放一次投射物，"飞→爆"自然衔接，不需要手动对齐两个时间点。

### 形态归并原则

不追求 13 种完全独立的几何，而是 **6 个母形 + 参数分化**：

| 母形 | 覆盖相性 | 分化参数 |
|---|---|---|
| 梭形（长条飞行体） | 剑 / 刀 / 腿 / 轻功 | 长宽比、是否带弧、尾长 |
| 团形（圆/方飞行体） | 拳 / 掌 / 毒 / 禅 / 奇门 | 是否带外环、是否自旋、散点数 |
| 针形（极细快体） | 暗器 | 连发数 |
| 波形 | 鞭 | 振幅 / 频率 |
| 爪形 | 兽 | 爪痕道数 |
| 交叉 / 弧面 / 钝击 / 扩散 / 收拢（命中母形） | 全部命中 | 见总表 |

这样 13 种相性只需约 9 个绘制函数，且新增相性时多数能直接复用母形。

## 3. 轨迹数学

统一记 `p = t / dur ∈ [0,1]`，锚点 `A`（释放者）→ `B`（目标）。

| 轨迹 | 公式 | 用在 |
|---|---|---|
| 直线 | `pos = A + (B-A) * ease(p)` | 默认 |
| 抛物线 | 在直线基础上叠加 `perp = (0,-1) * sin(p*π) * h`，`h = min(60, dist*0.18)` | 毒 |
| 波形 | 叠加法向偏移 `n * sin(p*π*2) * amp`，`amp = 8` | 鞭 |
| 自旋 | 投射物自身旋转 `rot = p * π * 2` | 奇门 |

**缓动**：`ease(p) = 1 - (1-p)^2`（ease-out，出手快、到点前略收），
与斩线同一族，保证手感一致。

**拖尾方向**：`dir = normalize(B - A)`，尾迹沿 `-dir` 画，长度随相性 26~40px。
⚠️ 拖尾是**短的**，不是从 A 到当前位置的一条长线 —— 那是 v0.1 明确否决的"通栏光缆"。

## 4. 时序与节奏

| 相性 | 飞 | 落 | 设计意图 |
|---|---|---|---|
| 暗器 | **0.12** | 0.14 | 最快最细，"看不见只听见"的偷袭感 |
| 剑 / 腿 / 兽 / 轻功 | 0.16 | 0.20 | 利落 |
| 刀 | 0.18 | 0.24 | 比剑重一拍 |
| 拳 | 0.20 | 0.26 | 钝、沉 |
| 鞭 | 0.22 | 0.24 | 有"甩出去"的过程 |
| 掌 / 奇门 | 0.24 | 0.28 | 内功要有余韵 |
| 毒 | 0.26 | 0.30 | 慢，渗出感 |
| 医 / 禅 | 0.30 | 0.32 | 最慢，与"杀人"在节奏上拉开 |

**距离自适应**：飞行时长不随距离线性增长（最远 1000px 时若等速会拖很久）。
采用"基准时长 + 距离微增"：`dur = base * clamp(dist/420, 0.85, 1.35)`，
保证近身不闪没、远距不拖沓，且**整体节奏仍由相性决定**。

**连击 / 重放**：多段伤害每段错开 40ms（与 v0.1 一致），形成连斩而非同时炸开。

## 5. 工程结构

在现有 `BattleFxLayer`（单 `Control` 自绘、64 条上限）上扩展，**不引入粒子与素材**。

```
Scripts/Game/UI/
  BattleFxLayer.cs        框架：FxItem / 池 / _Process 调度 / 消亡联动 / 通用几何
  BattleFxProjectile.cs   投射物：轨迹求值 + 6 个母形绘制（partial）
  BattleFxImpact.cs       命中：5 个命中母形 + 相性参数（partial）
```

`FxItem` 增加字段：

```csharp
public Category Cat;    // 相性：决定投射物形态、命中形与配色
public bool IsBolt;     // true=投射物（飞完自动生成命中），false=原地特效
```

**消亡联动**：`_Process` 里投射物走到终点时不直接删，
先按 `Cat` 生成一条对应的命中记录再删自己 —— 调用方无需关心两段对齐。

## 6. 数据补洞：相性从哪来

`BattleSkill` **没有** `Category` 字段（相性只在 `SkillConfig`）。

**不改引擎**，沿用 v0.1 处理 `DmgKind` 的思路：表现层建索引。

- `BattleManager` 启动时遍历 `ConfigManager.GetAll<SkillConfig>()` 建 `名字 → Category` 字典（与现有 `_skillKind` 并列）。
- `OnDamage(att, tgt, amt, skill)` 里把查到的相性一并传给 `PlayHitFx`。
- **普攻（skill = null）**：取攻击者 `Skills` 列表首门武学的相性作为"惯用兵器"；
  一门都没有时按 `DmgKind` 退化（外功→剑、内功→掌）。
- **DoT 不走投射物**：毒火每跳没有出手方向，仍用 v0.1 的泡 / 火星（否则每秒都在"出手"，逻辑错误）。

## 10. 表情贴图模式（2026-11-15）

用户决定战斗投射物/命中改用**贴吧表情包**。实现为**生成期预渲染贴图**，不用运行时系统字体画 emoji：
彩色 emoji 依赖系统字体回退，导出后跨平台会变黑白或豆腐块；贴图打包进游戏则无此问题。

- 素材生成：`.codebuddy/tools/GenFxTieba.py`
  90×90 白底 → 只抠与边缘连通的白色（保留内部牙白/眼白）→ 96×96 透明 PNG
- 输出：`Resources/UI/FxEmoji/fx_bolt_*.png` / `fx_impact_*.png` / `fx_cast.png`（27 张）
- 加载：`FxEmoji.cs` 按相性查表并缓存，**每种表情全局一张**，不为单卡重复出图
- 绘制：`DrawBolt` / `DrawImpact` / `DrawCast` 贴图优先，贴图缺失时回退到 v0.2 的程序化几何
- 尺寸：投射物 26~38px 随伤害占比缩放；命中 32~46px 由小放大再淡出

映射：投射物用"飞出去的脸"，命中用"挨打的反应脸"，13 相性各一张；起手固定用滑稽微笑。

## 11. 战斗原始观赏速度减半（2026-11-15）

用户：「战斗原始速度设为原来的 1/2（可以考虑调整行动条速度）」。

**结论：只改 `BattleManager.SimDtPerBeat`，行动条不需要单独调。**

推导链：
```
BattleClock.TickSec = 0.1s（真实节拍，UI 刷新频率）
  → BattleManager.OnBeat 每拍调 AdvancePlayback()
  → BattleReplay.Advance(dt) 里 T += dt，按模拟时间 T 取帧 / 派事件 / 贴回单位
  → 行动条 u.Gauge 由播片 ApplyFrame 贴回，与 T 同源
```
所以 `SimDtPerBeat` 决定**整个回放的时间轴**，行动条、伤害数字、特效时序一并同步。

| 项 | 改前 | 改后 |
|---|---|---|
| `SimDtPerBeat` | 0.15 | **0.075** |
| 相对真实时间 | 1.5 倍速观赏 | 0.75 倍（即原来 1/2） |
| `TickSec` | 0.1s | 不变（UI 仍 10Hz，画面更平滑） |
| 倍速按钮 | ×1 / ×2 / ×3 | 不变，仍可叠加 |

`SpeedFromSetting` 只认档位 {1,2,3}，所以**不能**靠把倍速设成 0.5 来实现——会被退回 1x。

⚠️ **副作用**：整场在入场时就已算完（`StartBattle` 的 ①），播片只负责回放；
改这一项不改变战斗结果与数值，但**每场回放时长翻倍**，推图/挂机节奏随之变慢。
若只想让画面慢而不影响挂机效率，需要另做"结算触发与回放结束解耦"，本次未做。

## 15. HDR 2D + shader 辉光层（2026-11-16）

用户：「搭配 shader、hdr2d 等技术，让战斗特效更好看」。

### 先验：HDR 2D 到底能不能用（不做这步后面全白搭）

`project.godot` 有 `viewport/hdr_2d=true` / `window/hdr/request_hdr_output=true`。
写探针画三块纯色，用 `Viewport.get_texture().get_image().get_pixel()` 读回：

| 输入 Color | 帧缓冲读回 | 说明 |
|---|---|---|
| (1, 1, 1) | (1.00, 1.00, 1.00) | 基准 |
| (3, 1, 0.5) | (**12.83**, 1.00, 0.214) | 超亮真实保留，sRGB→线性增益 |
| (8, 2, 1) | (**131.4**, 4.95, 1.00) | 同上 |

`format=14`（RGBA half float）。结论：**Color 分量可以 >1**，
叠加后能做出"过曝白核 + 彩色边缘"，而不是只能画不透明色块。
（注意读回的是线性值，所有截图仍须过 `FixShotSrgb.py`。）

### 架构：拆成两个 CanvasItem，而不是一个节点里堆效果

`blend_add` 与 `texture_filter` 都是 **CanvasItem 级**属性，两者需求冲突：

| 层 | 混合 | 过滤 | 职责 |
|---|---|---|---|
| `BattleFxLayer`（原有） | Mix | **Nearest** | 13 相性几何 / 像素序列帧，保形状与硬边 |
| `BattleFxGlow`（新增子节点） | **Add** | **Linear** | 只画光：光晕 / 拖尾 / 白核闪光 |

`BattleFxGlow` 通过 `BattleFxLayer.Items` 只读共享同一份 `FxItem`，
不复制列表、不另开定时器；父层 `_Process` 同时 `QueueRedraw()` 两层。
为让它能访问私有数据，`FxItem` 改 `internal`、`BoltPos/BoltDir` 改 `internal static`，
`SetupGlow()` 放在同文件的另一个 `partial class BattleFxLayer` 声明里 —— **public API 零变化**。

### shader（C# 内嵌，无 .gdshader 文件）

```glsl
shader_type canvas_item;
render_mode blend_add;
// fragment:
//   ① 以 UV 半径采样径向渐变贴图的 alpha，算柔化 falloff
//   ② R / B 沿半径反向偏移采样 (chroma) → 光晕边缘冷暖彩边
//   ③ COLOR.rgb（来自 modulate 的 HDR 超亮相性色）× gain 累加到背景
```

光晕贴图是全局一张 64×64 `GradientTexture2D`（径向，alpha 即光强），
不为每条特效生成。shader 负责把它收成圆润光晕并加色散。

### 三层光

| 效果 | 做法 |
|---|---|
| 投射物主光晕 | `1.85 ×` 投射物尺寸，HDR 相性色，随飞行略淡 |
| **连续光迹拖尾** | 沿 `BoltDir` 反方向 4 段，间距 `0.44 × core`，尺寸/alpha 递减，贴得够密才连成一条 |
| 命中白核闪光 | 命中头 35% 时长叠一小团 `Colors.White` 的 HDR 超亮光，形成"啪"一下过曝 |
| 其余种类 | 随 `sin(pπ)` 胀大淡出的柔光（DoT 泡/火星、起手更弱） |

`HdrLift = 1.25`、`shader gain = 1.5`、`chroma = 0.06`、`softness = 1.2`。
**浅色主题自适应**：`UIThemeManager.IsLightOf(UIThemeManager.Id)` 为真时
所有 alpha × 0.55 —— Add 混合叠到米白背景容易洗成一片白。

### 验证

- `dotnet build` 0 错 0 警；无头启动无 shader 编译错误
- 实机连抓 20 帧 + 差分选峰：峰值 **61350 → 61968**（改前无辉光约 14000），
  说明光晕确实铺开成可见变化
- **近白像素占比仅 0.02~0.06%**：没有过曝成白块，像素核心形状仍可辨
- `preview/fx_hdr_final_zoom.png`：蓝色拖尾连成光迹、命中带白核、
  绿色柔光、彩边可见，未遮挡卡底信息带

### 可调旋钮（都在 `BattleFxGlow.cs`）

| 想改什么 | 改哪里 |
|---|---|
| 整体亮度 / 过曝程度 | `HdrLift` 与 shader 的 `gain` |
| 彩边强弱 | `chroma`（0 = 无色散） |
| 光晕软硬 | `softness`（越大越集中） |
| 拖尾长度/连贯 | `DrawBoltGlow` 的段数、`0.44f * k` 间距 |
| 命中闪光时长 | `p < 0.35f` 那个窗口 |
| **整体关掉辉光** | 注释 `BattleFxLayer._Ready()` 里的 `SetupGlow()`，特效功能完全不受影响 |

### 风险与未做

- 每个 Bolt 最多 5 次 `DrawTextureRect`，64 条上限 → 每帧最多约 320 次绘制调用；
  实机 20 帧连抓无卡顿，但更低端设备需再压段数。
- 浅色主题只做了系数自适应，**未单独抓帧验证**（需切换 `SettingData.ThemeId`）。
- 没做真正的屏幕空间 bloom（亮度提取 + 高斯模糊 + 合成），
  那需要把特效渲染进独立 SubViewport 并改场景层级，改动面大；
  当前用"逐级放大柔光 + Add 累加"近似，成本更低且不动战斗结构。

### 15.1 两轮返工：从"洗掉细节"到"按形状发光"（2026-11-16 下午）

用户连续两条反馈：①「辉光好像让原来的特效细节没了」②「辉光应该按照特效的形状发光，现在只是个发光圆球」。

#### 第一轮：量化"细节没了"

播片确定性（`FxItem.Seed` 固定），关掉 `FxGlow.visible` 跑**同一时间轴**即可拿到同帧 A/B。
核心区（x800,y450 附近 50×50）：

| 版本 | 区域亮度 | 拉普拉斯细节方差 |
|---|---|---|
| 无辉光基线 | 27.8 | 6751 |
| v1 圆球辉光 | **159.6**（5.7 倍） | **2957**（掉 56%） |
| v2 降亮 + 中心衰减 | 45.2 | 6966（恢复） |

根因：`blend_add` 子节点画在核心**之后**，通用径向光晕直接叠在像素特效上，把高对比锐边洗平。

#### 第二轮：形状辉光（当前实现）

辉光不再用通用径向贴图，而是**复用 `FxPixel` 同一帧精灵表**，shader 做 8 邻域膨胀减原形状：

```
halo = max(8 邻域 alpha) - 当前 alpha
```

形状内部 `c == m` → `halo = 0`，**核心细节天然完整保留**；只有轮廓外一圈发光，
且光形完全跟着剑气 / 飞针 / 星芒走。拖尾也用同帧形状贴图的缩小版 → 残影是形状而非圆球。
`Cast / Bubble / Ember / Miss` 没有序列帧 → **不再给通用圆球光晕**，宁可不带辉光。
帧区域算法与 `BattleFxLayer.DrawSheetFrame` 严格一致（帧格 128、按 p 取 idx），否则错帧。

#### 四个踩坑（已修）

### 15.2 拖尾：从"复制图标"到轨迹残影（2026-11-16）

用户：「感觉拖尾有点奇怪」。放大 `preview/diag_trail.png` 后现象很具体：
卡间是 **4 个等大、等亮、等距、同一帧** 的竖向星芒簇排成一排，像条形码；
而且图案是竖直的、飞行方向是水平的，视觉上完全脱节。

#### 旧实现的三个问题

```csharp
Vector2 tail = pos - dir * (core * 0.52f * k);  // ① 直线排布
float ts = core * (1f - t * 0.40f);             // ② 0.9/0.8/0.7，和主体 1.24 差不多大
DrawShapeGlow(sheet, p, tail, ts);              // ③ 同一帧 p，形状完全相同
```

- ① 毒走抛物线、鞭走波形（`BoltPos` 里有偏移），直线拖尾直接脱节
- ② 尺寸递减太平缓，且间距 `0.52×core` 小于自身尺寸 → 大量重叠
- ③ 所有残影是同一帧图案，加上节点级 `gain` 无法按 draw 改亮度 → 等亮复制

#### 新实现（`BattleFxGlow.DrawBoltGlow`）

| 手段 | 效果 |
|---|---|
| 位置取 `BoltPos(it, back)`（过去时刻） | 贴合抛物线 / 波形；EaseOut 让间距自然不等距 |
| 帧进度用 `frameP = p - 0.10×k` | 残影是**更早的动画帧**，形状不再相同 |
| 尺寸 `0.68 / 0.44 × core` | 轮廓光面积按平方衰减 → 自然消散 |
| 段数 3 → 2 | 不再排成一长串 |
| `lag = min(0.055×k, p×0.60)` | 起手尾巴短；位置 lag 小才连得成短尾 |

**位置 lag 与形状帧 lag 刻意解耦**：位置用小 lag（靠得近才连成尾），
帧用大 lag（形状才不同）。第一版两者都用 `0.11`，EaseOut 在千像素轨迹上
拉开上百像素，尾巴断成几截孤立火花（`preview/compare_trail_final.png` 中栏），
减半到 `0.055` 后才定稿。

#### 验证

`dotnet build` 0 错 0 警，无头启动无 shader 报错；同帧（f11）三栏对比
`preview/compare_trail_final.png`：右栏残影连成短尾、尺寸递减、形状有差异，
主体轮廓光与像素核心细节不受影响。

可调旋钮：`0.055f`（尾巴长度）、`0.10f`（帧回退量）、`0.68f/0.24f`（残影尺寸）、
循环上限 `2`（段数）。

### 15.3 第三次收敛：半透明渐隐拖尾 + 辉光退成氛围（2026-11-16）

用户：「拖尾改成半透明到消失效果会好吗？现在的特效感觉和原始特效差距太大了，辉光干扰过头了」。

#### 先量化"干扰过头"

同帧（f11）与无辉光基线对比：

| 版本 | 全图平均差 | 核心区亮度 |
|---|---|---|
| 无辉光基线 | 0.00 | 27.8 |
| v1 圆球 | 1.15 | 159.6 |
| §15.2 形状辉光 | 0.50 | **69.8**（2.5 倍） |
| **§15.3 柔和版** | 0.38 | **36.7**（1.3 倍） |

形状对了但强度仍压过原始像素特效，用户判断成立。

#### 关键技术：让辉光强度能按 draw 控制

之前一直以为强度只能靠节点级 uniform，所以用"缩小尺寸"假装消散。
实际上 `draw_*` 的 **modulate.a 会进顶点色**，可以在 canvas_item **vertex shader**
里读 `COLOR.a` 并用 varying 传给 fragment：

```glsl
varying float vFade;
void vertex() { vFade = COLOR.a; }
// fragment: lit *= vFade;  COLOR = vec4(lit, halo * vFade);
```

于是 `DrawShapeGlow(..., fade)` 把 fade 放进 `modulate.a`，实现真正的
**半透明 → 消失**，不再需要靠尺寸陡减制造假消散。

#### 参数收敛

| 项 | 旧 | 新 |
|---|---|---|
| `BaseGain` | 1.6 | **0.75** |
| 主体光晕 fade | 1.0（隐含） | **0.42** |
| 命中光晕 fade | 1.0 | **0.36 × (1−0.5p)** |
| 拖尾段数 | 2 | **3** |
| 拖尾 fade | 全 1.0（靠缩小） | **0.26 / 0.13 / 0.087**（按 k 递减） |
| 拖尾尺寸 | 0.68 / 0.44（陡减） | **0.92 / 0.76 / 0.60**（只轻微递减） |

拖尾尺寸回归"几乎不变"，因为消散由 alpha 承担；残影读起来是同一个形状
逐渐淡去，而不是一串越来越小的图标。位置仍用 `BoltPos(back)` 历史轨迹、
帧仍用 `frameP = p − 0.10k`（§15.2 的成果保留）。

#### 验证

`dotnet build` 0 错 0 警、无头启动无 shader 报错。同帧三栏对比
`preview/compare_glow_soft.png`：右栏拖尾从亮到几乎不可见地淡出，
原始像素特效的锐边与粒子重新成为主角，辉光只剩极淡轮廓。
`preview/fx_soft_trail_zoom.png` 为拖尾放大。

#### 可调旋钮

`BaseGain`（整体辉光）、`0.42f` / `0.36f`（主体/命中）、
`0.26f / k`（拖尾渐隐曲线）、循环上限 `3`（段数）。
完全关闭仍只需注释 `BattleFxLayer._Ready()` 的 `SetupGlow()`。

### 15.4 主体"透明化"：给形状内部补一档自发光（2026-11-16）

用户：「特效主体有点透明化」。

#### 诊断：核心层没被削弱，是"内部零补光"

主体区域亮像素统计：无辉光基线 6673、形状辉光 7659、柔和版 6851 —— **核心像素本身没变**。
原因是 §15.1 的 dilation 刻意让形状内部 `halo = max(0, m - c) = 0`
（当初为保住锐边细节），代价是稀疏的半透明像素完全没有任何补光；
辉光一收敛，这些像素在暗背景上就显得"空、透"。中栏偏亮版反而更"实"，
正是因为当年通用光晕把内部也填满了。

#### 改动

shader 增加按**形状自身 alpha** 的内部微光，不回到洗细节的强光：

```glsl
uniform float inner_gain : hint_range(0.0, 1.0) = 0.30;
vec3 inner = shapeColor * c * inner_gain;   // c = 当前像素形状 alpha
vec3 lit = (vec3(轮廓光 R/G/B) + inner) * gain * 1.35 * vFade;
```

- 主体内部 `c>0` → 补一点自身颜色的光，把像素填实
- 轮廓外 `c=0` → 完全不加，光形仍严格跟着特效
- 乘 `vFade` → 拖尾渐隐不受影响
- 系数 0.30 很小，且 `BaseGain` 仍是 0.75，整体不会回到"干扰过头"

#### 验证与局限（如实记录）

- `dotnet build` 0 错 0 警；真实窗口探针确认 `FxGlow` 节点已挂载、
  `ShaderMaterial` 存在、`inner_gain=0.30` / `gain=0.75` 运行时值正确
- 实机帧 `preview/fx_solid_zoom.png`：绿色粒子主体内部有填充、不再空心发虚，
  无整片过曝，未盖住卡牌人物与信息带
- ⚠️ **严格同帧 A/B 这次未做成**：每次探针的战斗播片起始时刻会随加载耗时漂移
  （固定 f11 不再是同一战斗状态）；改用 `Engine.time_scale=0` 冻结画面切 uniform 的
  方案又恰好落在无活跃特效的时刻，两帧完全相同。所以本轮以**代码逻辑 +
  运行时状态 + 实机视觉**为准，不引用该组无效量化数据。
  若以后要做严格 A/B，需要在游戏内加一个"固定播片帧"的调试开关。
- 期间又踩了一次 verbatim shader 字符串里的 ASCII 双引号（"填实"），
  编译 27 错；已移除。**建议：shader 内注释一律不用引号。**

#### 可调旋钮

`inner_gain`（0.30，越大主体越实）、`BaseGain`（0.75，整体辉光）、
主体 fade `0.42`、命中 fade `0.36`、拖尾渐隐 `0.26/k`。
完全关闭仍只需注释 `BattleFxLayer._Ready()` 的 `SetupGlow()`。

### 15.5 辉光颜色与主体不一致：通道色散是根因（2026-11-16）

用户：「为什么原特效主体颜色和辉光特效颜色不一致」。

#### 结论先行

不是 HDR 2D、不是 sRGB 色彩空间、也不是素材本身的问题，
是 §15.1 里自己加的「冷暖彩边」把辉光整体染绿了。

#### 根因（可定量复现）

1. **主因 · 逐通道不同膨胀系数**

   ```glsl
   vec3(shapeColor.r * hr, shapeColor.g * halo, shapeColor.b * hb)
   ```

   R 只取横向 1.6 倍偏移、B 只取纵向 1.6 倍偏移，G 取 8 邻域全膨胀。
   `halo >= hr / hb` 恒成立 → G 通道系数恒最大，等于给整层辉光套了绿滤镜。
   用 `tmp/diag_glow_color.py` 逐像素复现 shader 数学（26 张精灵表）：
   旧公式平均色相偏 **58.3 度**、最大 **166.9 度**（掌 / 鞭等紫粉系最惨），
   26 张里 **24 张 G 通道恒为最大**。

2. **次因 · 取色是 9 像素 alpha 加权平均**

   白心加彩边的像素特效，轮廓外的光会变成两者的混合色，而不是主体本色。

3. **附带 · blend_add 的 alpha 二次衰减**

   `COLOR = vec4(lit, halo * vFade)`，而 `lit` 已含 `vFade` → fade 被乘两次；
   形状内部 `halo = 0` 使 alpha 为 0，§15.4 的内部补光实际上被吃掉了
   （这也是 §15.4 那次冻结 A/B 两帧完全相同的原因之一）。

#### 改动（只动 `BattleFxGlow.cs` 内嵌 shader）

- 取色改**邻域主导色**：9 个样本里挑 alpha 最大那个像素的 rgb；
  形状内部自然是当前像素自己，轮廓外就是离得最近、最浓的那块主体色。
- 三个通道统一乘同一个 `halo`，删掉 `hr` / `hb` 彩边。
- `lit = dominant * (halo + inner_gain * c) * gain * 1.35 * vFade`。
- `COLOR.a = 1.0`，fade 只在 `lit` 里出现一次，内部补光才真正生效。

#### 验证

- `dotnet build` 0 错 0 警；真实窗口启动无 shader 编译报错
  （新增自定义函数 `PickDominant` 不访问 `TEXTURE`，可被引擎正常编译）。
- 26 张贴图数学复现：平均色相偏差 **58.3 → 2.4 度**，
  G 通道恒最大 **24 → 8 张**（剩下 8 张素材本身就是绿色系，属正常）。
- `preview/glow_color_audit.png`：BODY / OLD glow / NEW glow 三列色卡，
  OLD 一列几乎全绿，NEW 一列与 BODY 逐行同色。
- `preview/fx_v3_palm_grid.png`：探针主动连发掌系投射物，实机四宫格里
  紫色主体配紫色辉光，无绿色光晕。
- ⚠️ **严格同帧 A/B 仍未做成**：冻结后切 `gain` 的两帧完全相同
  （冻结时特效层没有可重绘的活跃项，差分落在飘字 / 血条上）。
  本轮以 shader 数学复现 + 色卡 + 实机目视为准。若以后要严格量化，
  仍需游戏内加「固定播片帧」调试开关。

#### 经验

- HDR 辉光想保住主体色，**不要给 R/G/B 各配不同的强度系数**；
  色散若要加，只能作为同色亮度调制，不能替换通道配比。
- 形状外发光取色用「主导邻域色」比「邻域平均」忠实；平均会凭空造出第三种颜色。
- `blend_add` 下 `COLOR.a` 会再乘一次 src.rgb，fade 只应出现在一处。

## 17. 辉光特效跨引擎调研（2026-11-16，仅调研未改代码）

用户：「效果不好，联网查询一下别家辉光特效是如何做的，不限定 Godot 项目，
也可以参考 Unity / Unreal 项目」。完整报告见桌面
`轮回大侠/轮回大侠-辉光特效调研-v0.1.md`（含 19 条来源链接）。

### 核心结论

我们当前的 `BattleFxGlow` **不是 bloom，是单半径轮廓描边 + 加色叠加**。
三家引擎（Unity URP / Unreal / Godot 4）一致的标准管线是四步：
**亮度阈值提取（soft knee）→ 多尺度降采样金字塔 → tent 上采样按 lerp 归一化累加
→ 在 tonemap 之前用 screen / softlight 合成回 HDR 原图**。
差的是范式不是参数，所以前五轮调 `gain` / `fade` / `inner_gain`
一直在「细节被洗掉 ↔ 辉光看不见」之间来回摆。

### 差距速查

| 维度 | 业界 | 我们 |
|---|---|---|
| 光形 | 多尺度（紧 halo + 宽外溢） | 单 pass 8 邻域 dilation，只有一圈 |
| 提取 | 亮度阈值 / 能量守恒 | 无阈值，形状 alpha 全部参与 |
| 核心 | 只画一次，保持锐利 | 辉光层放大 1.24 倍又画了一次 |
| 混合 | Screen / Softlight 为主 | `blend_add`（Godot 官方称通常太强、无法使用） |
| 选择性 | 独立 emissive layer | ✅ 已对齐，保留 |

### 2D 像素风的三条底线

1. 核心层只画一次、保持锐利，辉光层绝不重画主体；
2. 只对特效 / 高亮层发光，卡面、UI、背景不参与（selective bloom）；
3. 优先 screen / softlight，别用强 additive；能量用归一化累加。

### 三条待选路线（等用户拍板）

- **A 轻量**：保留现有节点，shader 内做三层软膨胀 + 亮度阈值 + 不再重画核心。改动小、可回退，仍是单 pass 近似。
- **B 正统**：`SubViewport` / `hint_screen_texture` 多级 mip 做真金字塔 + screen 合成。最接近别家，但要动场景树与 HDR 链路，风险高。
- **C 素材向**：离线给 26 张 `fxp_*.png` 预烘焙 2 层多尺度 halo，运行时核心 + halo 直接叠。像素风最稳、零后处理开销、符合项目「素材预生成」偏好。

推荐 **先 A 后 C**，B 留到需要全屏大范围光溢时再上。

## 18. 落地路线 B：改用引擎原生多尺度 Glow（2026-11-16 晚）

用户拍板选 **B 正统多尺度金字塔**。

### 关键判断：不与引擎重复实现

调研时把 B 想成自搭 `SubViewport` 降采样链，但 **Godot 的
`WorldEnvironment` Glow 本身就是那套管线**（HDR 阈值 → glow levels 多尺度
降采样 → 上采样累加 → tonemap 前 Screen 合成）。按项目「框架已提供的能力
不要自己再实现一遍」的约定，直接用引擎实现，比自研渲染链稳得多，
也不用动场景树 / `CanvasLayer` / `BackBufferCopy`。

### 先验探针（技术前提，不做这步后面全白搭）

`tmp_probe_envglow.gd`（临时，已清理）：动态加 `WorldEnvironment`，
`BG_CANVAS` + `glow_hdr_threshold=1.0` + 7 级全开，画面放两个测试块：

| 测试块 | 颜色 | 结果 |
|---|---|---|
| HDR 块 | `Color(3.0, 1.4, 0.5)` | **发光**，且是多尺度柔光 |
| 普通块 | `Color(0.9, 0.5, 0.2)` | **完全不发光** |
| 卡面人物 / 边框 | 贴图原色 | **完全不发光** |

→ 引擎 2D Glow 生效，且 **selective 不靠 layer mask，靠 HDR > 1 自动达成**。
但默认参数光溢半径约 400px，把半屏染成橙色，必须收敛。

### 6 组参数扫描

`tmp_scan_envglow.gd` 扫 emissive 倍数 / intensity / 开启层级 / hdr_scale，
`preview/scan_envglow_grid.png` 为对比。第 0 组（int 0.50、只开 1~3 级）
最克制：紧贴一圈柔光、方块不过曝、背景不被染亮；第 3 组（开到 5 级）
整片泛红，正是 UE 文档警告的光污染。

实战是稀疏像素特效，HDR 总量远小于实心方块，所以最终取
**`GlowIntensity = 0.70`、只开 1~4 级**（介于第 0 / 2 组之间）。

### 架构改动（两个文件）

| 文件 | 改动 |
|---|---|
| `GameRoot.cs` | 新增 `SetupGlowEnvironment()`，在 `_EnterTree` 里注册 `WorldEnvironment`：`BG_CANVAS`、`GlowHdrThreshold=1.0`、`GlowBlendMode=Screen`、`GlowBloom=0`、前 4 级 |
| `BattleFxGlow.cs` | **整体重写为 HDR 发光源层**：只把同尺寸同帧的特效像素推到 > 1，辉光交给引擎 |

`BattleFxGlow` 的具体变化：

- shader 从「8 邻域 dilation + 彩边 + 主导色 + inner_gain」简化成
  `render_mode blend_add` + `COLOR = vec4(t.rgb * t.a * COLOR.rgb, 1.0)`；
  手动乘 `t.a` 是因为 blend_add 下 alpha 固定 1 不会自动衰减。
- `DrawShapeGlow` → `DrawEmissive`，尺寸与核心层**严格一致**，
  删掉放大 1.24 倍那次重画（旧版主体重影的来源）。
- fade 乘进 `tint.rgb`、alpha 固定 1，避免 `blend_add` 二次衰减。
- 删除 `BaseGain` / `inner_gain` / `spread_px` / `hr` / `hb` / 主导色 /

### 结论：别家是同一套节拍

蓄力 → 前冲 → 命中（顿帧 / 震屏）→ 回弹 → 归位；位移交给 Tween/Sequence，

`LungePx=40`（初版 26，用户指定 36~44 取中值）/ `LungeIn=0.02` /
`LungeHold=0.03` / `LungeOut=0.11`。
前冲压到 2 帧是为了让接触帧与 `OnDamage` 当帧的飘字 / 命中特效对齐；
`LungeHold` 只是局部停顿，**不是全局 hitstop**（不动 `Engine.TimeScale`，

## 22. 对撞加弧线轨迹与 ZIndex 抬升（2026-11-16 21:2x）

> **后续更新（见 §24）**：本章的 **ZIndex 抬升已于同日删除** —— 同帧 A/B 实测
> `z=-20` 与 `z=-40` 的截图 **MD5 完全相同、0 像素差异**。弧线轨迹与负层级带保留。
> 下面关于抬层的描述是当时的过程记录，不再是现状。

### 需求与结论

在「全部攻击微对撞」基础上让它更抓眼，只加两项：
**接触帧抬层**（前冲卡压在其它卡之上）+ **弧线轨迹**（不再是纯水平滑步）。
已落地并实机验收通过；命中帧对齐、总时长 0.16s、`LungePx=40` 均未改动。

### 关键决策一：负 Z 带，而不是正数抬升

`ZIndex` 是**全局**排序。UIManager 把 MainPanel（导航条 / HUD）与天赋、卡册等
弹窗面板都挂在同一 canvas layer 下，根节点 `ZIndex` 默认 0。
若把前冲卡抬成正数，弹窗打开时会出现「一张卡浮在半透明遮罩前面」——
这是设计文档 §5 的 B 级失败信号，且靠调参无解。

因此新建 `BattleZ`（放在 `BattleLayout.cs` 末尾，唯一定义处），
把**整片战场**排在 0 以下，抬升只在带内发生：

| 层 | ZIndex | 说明 |
|---|---|---|
| `TBg` 背景 | -50 | 最底 |
| 静止卡 | -40 | `HeroCardLayer.BuildOne` 设 |
| `TStacks` 召唤堆叠 | -35 | |
| **前冲卡** | **-20** | `PlayLunge` 期间，结束复位到 -40 |
| `TFx` 战斗特效 | -10 | `EnsureFxLayer` 设 |
| `TFxLayer` 飘字 | -5 | |
| `TResult` / 按钮 | -1 | |
| HUD / 所有弹窗面板 | **0**（默认，不改） | 天然在整片战场之上 |

实机探针：`TalentPanel z=0` 且前冲卡 `z=-20` 同屏 → 弹窗完整覆盖、无卡穿透。
只给「层」设一次即可 —— `CanvasItem` 默认 `ZAsRelative=true`，子节点 z 会累加父节点，
卡内部的信息带 / 出手横幅会跟着整卡一起抬升。

### 关键决策二：弧线主体放在 Hold 与回程，不放去程

最初按常规写「去程抛物线拱起 + 回程下沉」，实机采样打脸：
`LungeIn=0.02s` 约 **1 帧 @60fps**，抛物线中途一帧都采不到，去程只留 `-1.5px`，
肉眼看等于直线；弧线全靠回程 `+6.8px` 在撑。
又不能拉长 `LungeIn`（会破坏命中帧与 `OnDamage` 飘字对齐，§20 已定），
于是改成 **接触点上抬 + 回程斜向下收回并带下沉弧**：

- `_lungePeak = BasePos + (dir * 40, -10)` —— 峰值本身就抬起 10px，
  Hold（约 2 帧）与回程（约 7 帧）都能读出弧线；
- `DashStep(p)`：`Position = Lerp(_lungeStart, _lungePeak, p)`；
- `ReturnStep(p)`：`Lerp(_lungePeak, BasePos, p)` 再叠 `+ ArcY(p) * 1.0f`；
- `ArcY(p) = 10 * 4p(1-p)`，p=0 / 1 时为 0，所以起终点严格是 `BasePos`，纵向零漂移。

回程系数第一版取 0.55，被 Back 缓动把 y 插值很快推回 0，**下沉只剩 +1.1px、
轨迹退化成往返直线**；提到 1.0 后去程与回程路径才真正围出闭合弧。
全程缓动仍交给 Godot `Tween`（`Quad/Out`、`Back/Out`），没有手写插值公式。
两段都用 `TweenMethod`：两条 tween 抢同一个 `position` 会互相覆盖。

## 23. 对撞轻微 Scale + 8 套主题逐套验收（2026-11-16 21:4x）

### 23.1 Scale：Node2D 没有枢轴，必须在 Position 里补

第一版想用 `PivotOffset = Size / 2` 把缩放枢轴放到卡中心，**编译直接报 CS0103** ——
`PivotOffset` 是 `Control` 的属性，`Node2D` 根本没有枢轴概念（transform 原点就是节点原点）。
不补的话，放大 1.04 会让卡向右下甩出 `Size*(s-1)/2`。

改成在位置里显式补偿：

```
CenterShift(s) = (1 - s) * Size * 0.5
DashStep(p)   : Scale = Lerp(1, LungeScale, p);      Position = Lerp(start, peak, p) + CenterShift(Scale.X)
ReturnStep(p) : Scale = Lerp(LungeScale, 1, p);      Position = Lerp(peak, base, p) + CenterShift(Scale.X)
```

三个细节：

1. **Scale 与 Position 必须在同一个 `TweenMethod` 里写**。拆成「一条 tween 改 scale、
   一条改 position」会读到上一帧的缩放值，抖一帧；而且 `Kill()` 时容易只复位其中一条，
   缩放卡在半途。
2. **连击时要先反解补偿**：`_lungeStart = Position - CenterShift(Scale.X)`，
   否则卡正停在放大半途时再攻击，起点会多算一次补偿，位置跳一下。
3. **点击命中框不能用 `GlobalPosition + Size`**。缩放后 `GlobalPosition` 已不等于渲染左上角，
   改成用 `GlobalTransform` 变换两个对角：
   `Rect2(xf * Vector2.Zero, xf * Size - xf * Vector2.Zero)`。
   `UpdateTilt` 的卡中心同理改 `GlobalTransform * (Size * 0.5f)`。

`LungeScale = 1.04`（卡宽 203→211、高 261→271，列间距 26px 仍有余量）。

## 24. ZIndex 抬升实测无效，已删除（2026-11-16 21:5x）

### 起因

用户质疑：「Godot 2D 的 ZIndex 抬升好像没什么用，要清除掉相关代码么？」

不靠推理回答，直接做同帧 A/B：冻结 `Engine.time_scale = 0`，把 **8 张卡全部**
定格在前冲峰值姿态（`+40 / -10`、`scale 1.04`，重叠最严重的状态），
只切换 `z_index`，抓两张图。

**结果：MD5 完全相同，0 / 2073600 像素差异。**

### 为什么零效果

- 布局：后排卡右边缘 `589`、前排卡左边缘 `599`，间距只有 10px；
  前冲 40px 后右边缘到 `629`，与前排卡重叠 **30px** —— 看起来确实该抬层。
- 但 `HeroCardLayer.Build` 按 index `0..3` 建卡：`a[0]` 是前排、树序最前（画在最底），
  `a[1..3]` 是后排、树序在后（画在上面）。
  **所以后排卡前冲时本来就画在前排卡之上**，抬层没有改变任何绘制顺序。
- 前排卡前冲：右边缘 `858`，敌方前排左边缘 `940` —— 根本不重叠。
- 结论：任何单卡前冲都不存在「需要压住、但树序压不住」的情况。

### 处理：删抬升，留层带

| 项 | 处理 | 理由 |
|---|---|---|
| `BattleZ.CardLunge`（-20） | **删** | 0 像素差异，且多一份必须复位的状态（A 级失败信号来源） |
| `PlayLunge` 里的 `ZIndex = CardLunge` | **删** | 同上 |
| `ResetLunge` 里的 `ZIndex = CardIdle` | **删** | 一旦不再抬层，就没有可复位的东西 |
| `BattleZ` 其余 6 个常量 | 原本**留**，当晚也删（见下） | 不改变画面，只是把树序复述成常量 |

判断标准：抬升属于「不能解释制造了什么玩家决策 / 可感知反馈」的系统 → 删。
以后若做「双方同时冲到中线」（方案 C），两张卡会真正互相重叠且谁压谁取决于方向，
那时再按需加回抬升。

### 追加：负层级带也在同一晚删除（22:5x）

用户随后要求「清掉」整组。删前先做等价性验证：**同一次运行内**、冻结战斗、
定格同一姿态，**z 全 0** 与**手动设回旧负带 `-50..-1`** 两张图
**MD5 完全相同、0 像素差异**。负带同样只是在复述树序，不改变任何画面。

（顺带排除一个假警报：清理前后跨运行对比曾出现 114539 像素、max 561 的差异，
看起来像层级坏了。定位后发现差异分布在卡牌列与血条上，是两次运行战斗进度不同
导致的血量、飘字、特效相位差异 —— 同运行 A/B 为 0 差异，证实与 z 无关。
**跨运行比图不能用来判断"某行代码有没有视觉作用"，必须同运行、只改一个变量。**）

删除范围：

| 文件 | 删除内容 |
|---|---|
| `BattleLayout.cs` | 整个 `BattleZ` 类（文件已回到加它之前的状态） |
| `BattlePanel.cs` | `SetupZOrder()`、`SetZ()`、`_fx.ZIndex` |
| `HeroCardLayer.cs` | `card.ZIndex = BattleZ.CardIdle` |

现在层级完全靠树序，探针实测 `index 0..6` 全 `z=0`：

```
idx=0 TBg(背景) → idx=1 UnitsArea(→TCards→TStacks) → idx=2 TFx(特效)
→ idx=3 TFxLayer(飘字) → idx=4 TResult → idx=5/6 结算按钮
```

`MainPanel` 在 GameRoot 里比 `BattlePanel` 后 `ShowPanel`，HUD 与弹窗自然在其上。
只在 `BattlePanel.EnsureFxLayer` 旁留了一句注释说明这个顺序 —— 那里会用 `MoveChild`
动态插层，是唯一会动树序的地方。

**为什么留注释而不是留代码**：负层带是「把树序复述成常量」，属于第二事实源。
树序一旦被改，两边不一致反而更难查（会以为是 z 的问题）。一句注释足够说明约束，
且不会漂移。

### 回归验证

- `dotnet build` 0 错 0 警；运行时无脚本 / shader / 资源报错。
- 删除后用同样姿态定格再抓一张，与删除前 `z=-40` 那张比：
  1306 / 2073600 像素差异、**每像素差值 ≤ 2** —— 属跨运行的渲染噪声（战斗状态随机、
  血条动画相位不同），不是结构变化。
- 8 张卡的 `z_index` 冻结时全为 `-40`（由 `BattleZ.CardIdle` 设），层级带正常。

### 教训

这轮先加了「抬升」再删，绕了一圈。根因是当初把「视觉上想让前冲卡压住别人」
当成了需求，却没先确认**当前布局下到底会不会重叠、重叠时谁在上**。
以后加层级/遮挡类效果前，先算一遍矩形相交与树序，再决定要不要写代码。
