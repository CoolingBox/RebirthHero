# 《轮回大侠》卡牌边框设计 v0.1

> 2026-11-14 · 8 套中式框景 · **素材只有 8 份，颜色全靠 Modulate**

---

## 0. 素材观：形状与颜色分离

卡牌边框最容易做成"每个品阶 × 每个阵营 × 每个主题各出一张图"，素材量滚雪球。
本设计把**形状**和**颜色**彻底拆开：

| 层 | 内容 | 数量 |
|---|---|---|
| 纹样（形状） | `Resources/UI/Borders/border_*.svg`，白色 + 透明底 | **8 份，全局唯一** |
| 纹理缓存 | `CardBorderFactory._cache`，同种纹样只加载一次 | 运行期 8 张 |
| 颜色 | `NinePatchRect.Modulate`，由调用方给 | 0 份额外素材 |

所以"多套边框"不等于"多份素材"。改颜色不需要出图，加一套新颜色主题是零成本。

---

## 1. 八套纹样

刻意**不采用**"白绿蓝紫橙"那套西幻品阶色与对应的通用纹样，改走中式框景：

| 纹样 | 意象 | 几何特征 | 默认用于 |
|---|---|---|---|
| **宣纸** | 纸 | 毛边细框（多段抖动折线），四角无饰 | 品阶 1 |
| **回阑** | 栏杆 | 双边 + 方形回纹，不断头 | 兜底默认 |
| **流云** | 云 | 卷云角 + 四边断云 | 品阶 3 |
| **竹节** | 竹 | 边线分节、节疤加粗 + 四角竹叶 | 品阶 2 |
| **寒裂** | 冰 | 角部冰裂发散 + 边中点菱形 | 品阶 4 |
| **金锷** | **剑装** | 上下剑首（圆首+内环）、四角剑锷、两侧剑脊 | 品阶 5 |
| **锁甲** | 甲 | 粗边 + 连续半圆鳞甲 + 角部铆钉 | 首领 |
| **血缕** | 血沁 | 裂边 + 角部血滴下淌 | 魔性卡（备用） |

**金锷**是其中唯一有"兵器结构"的：看轮廓就知道是剑，不靠颜色区分。
这是武侠语境下的边框语言，西幻那套"宝石镶边"在这里不适用。

---

## 2. 复用发生在三层

**① 生成期：纹样单元只写一次**
`GenBorders.py` 里每套角饰是一个函数，四角靠 `transform` 旋转复用。
SVG 里**不用 `<defs>/<use>`**（Godot 的 ThorVG 对 `use` 支持不完整），
而是生成期就展开成普通 path —— 复用写在代码里，产物自包含。

**② 加载期：同种纹样全局一张**
`CardBorderFactory.Get(kind)` 命中字典缓存，8 张卡共用同一张纹理。

**③ 使用期：颜色只改 Modulate**
品阶换纹理、阵营换颜色，两者互不出图。

---

## 3. 九宫格

SVG 为 **96×96**，四角 **24×24** 是纹样区，`PatchMargin = 24`。

- 角部纹样恒定 24px，**不随卡尺寸变形**
- 边部只有线没有纹样，横竖拉伸不会拉花
- 线宽保持 SVG 原值（1.2~2.6px），卡面 203×261 下读得清

---

## 4. 数据链：品阶从哪来

`BattleUnit` 原本没有品阶字段，本次补上：

```
HeroConfig.Rarity ──→ HeroBuilder.Build(u.Rarity) ──→ BattleEngine.Clone 跨波带上
                                                            │
                                          BattleParallaxCard.Setup
                                                ForRarity(u.Rarity) → 纹理
                                                敌我 → Modulate 颜色
```

- `Rarity = 0` 表示未指定，回退到回阑（不会拿到空纹理）
- **纹样表达"什么货色"，颜色表达"哪一边"** —— 两条信息不混用，
  所以敌我识别方式与改动前完全一致。

---

## 5. 怎么新增一套边框

1. `GenBorders.py` 里加一个 `border_xxx()` 函数（角饰用 `four_corners()` 复用）
2. 在 `BORDERS` 列表登记（key / 名称 / 说明 / 建议色）
3. 重跑生成器 → 多一个 SVG
4. `CardBorderFactory` 的 `CardBorderKind` 与 `Files` 各加一项（**顺序必须对齐**）
5. 需要默认配色就在 `SuggestColor` 里补一条

不需要碰卡牌代码，也不需要为任何颜色补图。

## 8. 实机检测与修正（2026-11-14 晚）

无头模式验证不了视觉，改用**真实窗口跑游戏 + `Viewport.get_texture().get_image()` 抓帧**，
拿到了 1920×1080 实机画面。三个问题的根因与纸面设计完全不同：

### ① 边框过重 —— 真凶是素材，不是代码

`L4.png` 是素材**自带的亮金色回纹框**（满圈卷云，与主题无关）。
所以 8 套主题下边框全是金色，且与程序化边框叠成**双重边框**。

**修正**：`LoadArt` 里停用 L4（`Visible = false`），边框统一由 `CardBorderFactory` 承担。
此前"多套边框"在素材金框压着的情况下根本看不出来。

### ② 人物太小 —— 留白被算进了排版

`LayoutCharOver` 原用固定 `CharAspect = 896/1152` 排版，但源图人物本体只占约 60% 宽，
**四周透明留白也参与尺寸计算**，人物本体被稀释到卡宽 45%，全身像的头部只剩约 20px。

**修正**：
- 新增 `.codebuddy/tools/CropPortraits.py`，把 65 张 L2 裁到 alpha 边界（留白 37–65%），
  原图保留为 `L2_raw.png` 可回滚
- `LayoutCharOver` 改为**按纹理真实宽高比**排版（裁剪后每人比例不同）
- `CharScale` 1.10 → **1.35**

### ③ 背景与人物争夺注意力

L1 背景是亮黄褐色战场。**修正**：背景层 `Modulate = (0.70, 0.70, 0.73)` 压暗压灰，
它是"舞台"不是主角。

### 复测

修改后实机抓帧对比：人物明显变大且全身可读、边框退回阵营色不再抢眼、背景压暗人物突出。
**经验：视觉问题必须实机抓帧验证，无头装载通过不等于画面正确。**

### 第三轮：边框分量与人物构图（同日晚复测）

v2 修正后又暴露新问题：**边框太弱被背景淹没**、**人物破框过多**。
根因是把"边框克制"误当成了目标 —— 实际需求是**边框要压得住背景**。

| 调整 | 改动 | 说明 |
|---|---|---|
| 边框加粗 | `GenBorders.STROKE_SCALE = 1.8`，统一作用于 `stroke()` / `rect_path()` 及两处硬编码线宽 | 96px 画布上的细线铺到 203×261 卡面后太弱 |
| 边框提亮 | `Modulate = borderColor.Lightened(0.45f)` | 主题里的阵营描边色偏暗，直接用会被整幅画淹没 |
| 人物构图 | `CharScale` 1.35→**1.05**，改回**按整卡高排版、底边对齐卡底** | 上半身因此更大，小腿由信息带自然裁掉 |

关键认知转变：**卡牌人物要"大"，不要求"全"**。
此前为了保住全身而按可见画区缩小排版，导致脸读不出；现在让信息带裁掉小腿，换取上半身与脸部的可读性。

三版实机对比：`preview/compare_v123.png`（v1 原始 / v2 人物大边框弱 / v3 边框强 + 上半身）。

### 第四轮：背景溢出（"背景比边框大一圈"）

**根因**：`_art` 容器从未设置 `ClipContents = true`，而背景层 L1 为视差被放大 20px
（`PadSize = 10`，位置 `-pad`、尺寸 `Size + pad*2`）。没有裁剪，背景就直接溢出到边框外一圈。

代码里只有卡根的 `ClipContents = false`（故意给人物破框用），
注释却写着"由内部的 `_art` 自己 ClipContents 管住" —— **注释与实现不符**，这层裁剪一直没写。

**修正**：`BuildArt` 里补 `_art.ClipContents = true`。
背景被裁到卡面，视差时仍有 20px 余量不会露边；人物溢出层挂在卡根、不在 `_art` 内，不受影响。

**经验**：注释里声称的约束要去代码里核实。这条"由内部管住"的注释存在了至少两轮迭代，
实际一行裁剪都没写。

### 第五轮：边框线宽（"还是细"）

`STROKE_SCALE` 1.8 → **3.0**。

九宫格拉伸时线宽不被缩放（横边只拉长、竖边只拉高），所以卡面上的线宽就是
`SVG 原始值 × STROKE_SCALE`。1.8 倍在 203×261 卡面上仍不足，3 倍后框架感才成立。

注意**不同纹样的"视觉厚度"不同**：回阑是双线（外粗内细）所以看起来比宣纸的单线厚。
若希望所有卡都有一致的厚框感，统一用回阑/金锷这类双线或粗边纹样，而不是继续堆倍率。

## 9. 改用 AI 生图边框（第六轮，SVG 方案被否决）

用户反馈"现在边框就是一条实线，不要用程序化生成的，使用生图模型"。
**SVG 矢量线框确实出不来金属厚度与浮雕细节**，第六轮改为 AI 生图素材。

### 流程

```
ImageGen（绿幕 #00FF00 + 满幅贴边提示词，1024×1536）
   → 绿幕键控转 alpha（greenish 判定 + 到纯绿距离软边 + 四边 floodFill + despill）
   → clamp_outward 边缘延展（限最外 12px）
   → 缩放到 406×522（2 倍卡面）
   → Resources/UI/Borders/frame_*.png
```

出图提示词必须显式写两条，否则必返工：
- **满幅贴边**（"边框外沿与四边完全重合、之外没有任何留白、不要居中的小画框"）
- **中央纯绿均匀无渐变**（供键控）

### 踩过的三个坑

| 坑 | 现象 | 处理 |
|---|---|---|
| `int16` 溢出 | `b*b` 最大 65025 超过 int16 上限，距离算错，边框被当背景抠掉 | 键控全程 **float32** |
| `clamp_outward` 无范围限制 | 某列顶部边框被抠透明时，底部边框被一路填到画面中心，污染镂空区 | 延展限制在最外 **12px** |
| 按 `sorted()` 顺序命名 | 中文文件名排序 ≠ 生成顺序，剑装与回纹**名字标反** | 按**文件名关键词**命名，不用顺序索引 |

### 渲染方式随之改变

AI 边框是**固定比例的整幅卡框**，不能用九宫格（会把浮雕拉花）：
`NinePatchRect` → `TextureRect`（`StretchMode = Scale` 铺满卡面）。

并且**不再整体染色**：SVG 是白纹样必须染色，AI 边框自带青铜金属色，
整体染色会毁掉质感。现在只给轻微阵营倾向（我方 `0.88,0.95,1`，敌方 `1,0.8,0.8`）。

### 当前状态

已出 **2 套样张**：剑装（青铜鎏金，品阶 ≥4）/ 回纹（青铜回字，默认）。
其余纹样可复用同一流程补齐：`GenBorders` 的 SVG 不再参与渲染，仅作历史保留。
抠像脚本已归档 `.codebuddy/tools/CutFrames.py`。

## 10. 风格修正 + 镂空（第七轮，最终）

用户否决第六轮："这种质感的边框和项目不搭"，并追加"最好带有些许镂空"。

**诊断**：青铜写实金属框是西式厚重材质语言，项目卡面是**国风水墨插画 + 扁平 UI**，冲突。
原素材 L4 那种细金线平面装饰框才是搭的。

**重新出图**（平面线描，明确否定写实金属 / 三维浮雕 / 西幻），两套：
- 鎏金回纹：金线回字纹 + 卷云角 + 朱砂小印
- 水墨卷云：淡墨卷云 + 竹叶 + 朱砂点

**"些许镂空"怎么来的**：这两张图中央纯绿、但边框外圈是米白宣纸底。
只抠绿会留一整块米白盖住卡面插画，因此用**绿幕 + 宣纸底色双键控**，把底也转透明，
只留线描纹样 —— 线间自然镂空，透出下面的卡面。

### 双键控踩坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 四角采样底色 | 角上有卷云纹样，底色采暗，亮度判据整体失效 | 取全图**最亮 12% 像素**的中位作底色 |
| 只用颜色距离 | 淡墨线与米白底距离小，水墨框被抠成几乎全透明 | 亮度差 + 饱和度 + 颜色距离**三判据取并集** |
| 四边 floodFill | 宣纸底有微弱 alpha，连通区从边缘蔓延全图，金线被一起清掉 | 纯绿区已由绿幕判定清零，**去掉 floodFill** |
| despill | 对所有半透明像素压 G，暖金线与宣纸噪点全染成洋红 | 本批图边缘无溢色，**不做 despill** |

最终两套：回纹 17.8% / 卷云 5.4% 不透明像素，中央全透明、线间镂空、无色偏。

### 渲染

- 停用了不搭的 `frame_jine.png`（青铜写实），当前素材只有 `frame_huilan.png` / `frame_liuyun.png`
- 高品阶 → 卷云，其余 → 回纹（`ForRarity`）
- **不做任何染色**（`Modulate = White`）：平面线描的金/墨/朱砂配色染红染青都会毁掉它，
  敌我改由站位与卡牌底色区分

实机风格对比：`preview/compare_ai_styles.png`。平面边框抠像脚本 `.codebuddy/tools/CutFlatFrames.py`。

## 11. 实机截图的颜色空间（重要方法论修正）

**问题**：用户发现实机画面与截图有色差。

**确诊**（纯色探针，不靠猜）：
探针画一块 `Color(1, 0.5, 0)`，理论 sRGB 为 `(255,128,0)`；
`root.get_texture().get_image()` 取回 **`(1, 0.214, 0)`**（线性值），
对它做 `linear_to_srgb()` 后回到 `(1, 0.4999, 0)` ✓。

**根因**：`Viewport.get_texture().get_image()` 返回线性帧缓冲，
直接 `save_png()` 写盘后查看器按 sRGB 解释 → 截图整体发黑、饱和度偏高。
窗口显示时驱动会正确编码 sRGB，所以实机比截图亮且柔和。

**影响**：本文档第 8–10 轮的所有视觉判断都基于**偏暗的错误截图**，
其中"背景 Modulate 压到 0.70""边框加粗 3 倍""边框提亮"等有可能是对错误画面的过度补偿，
**需要在正确 sRGB 画面下重新评估**。

**修正工具**：`.codebuddy/tools/FixShotSrgb.py`
```
python FixShotSrgb.py <截图.png>          生成 *_srgb.png
python FixShotSrgb.py --all <目录>        批量
```
以后每次抓帧都要过一遍，或直接在探针里做 sRGB 编码后再存盘。

## 12. "背景比边框大一圈"最终修正

在正确 sRGB 画面下重新看，用户反馈仍成立，但根因与前几轮都不同：
**AI 线描边框是镂空的，插画背景一路铺到卡面最外沿**，金线回纹像"贴在画上的一圈花纹"，
而不是"框住画的边框"。

先后排除了三个误判：
- 不是背景溢出**卡外**（第 4 轮已用 `_art.ClipContents` 修过）
- 不是只差一圈实体边（第 8 轮加的 10px `_frameBacking` 盖不住回纹与卡边之间的背景）
- 抠像残留的米黄底已二次键控清掉（回纹 17.8%→7.5%，外沿 α=0）

**最终修法**：把画区整体内缩，插画只从金线内圈开始。
```
EdgeW = 12 / ArtInset = 12
_art.Position = (12, 12)
_art.Size     = Size - 24
_frameBacking 实体边宽 12（主题 panel_border 色）
```
`_art` 内 `L1` 仍有 10px 视差余量，被 `ClipContents` 裁到内圈，不露边。
人物 `_charOver` 挂在卡根不内缩，保留刻意的人物破框（Marvel Snap 式"人先出画"）。

放大图：`preview/v10_card_zoom.png`；前后对比：`preview/compare_v9_v10.png`。
要调整边框占比，改 `ArtInset` 与 `EdgeW`（两者应保持一致）。

## 13. 边缘毛糙清理（2026-11-16）

用户反馈「卡人物牌边缘毛糙」。放大单卡 3 倍定位，发现两处，性质完全不同：

**① 人物轮廓的金色圈 = 原画自带 rim light，不是缺陷。**
查看 `L2.png`（透明底合成深色底放大）确认：那圈金线平滑、连续，
沿发梢/肩/手臂分布，是 AI 生成立绘的轮廓光。**不应处理**，去掉会破坏美术。

**② 卡框线描外侧的细碎白点 = 双键控抠像残留的半透明软边。**
`frame_huilan.png` 半透明(8~250)占比 5.4%、`frame_liuyun` 更高，
在深色卡面上呈雾状毛点。这才是"毛糙"。

### 处理（`.codebuddy/tools/CleanCardEdges.py`）

- 卡框：`alpha>=160` 保实 255、`alpha<90` 清零、中间留窄过渡；
  再按连通域清掉面积 <6px 的孤立碎点。
  试过线性拉伸阈值 140，会把线描主体压成半透明（实心只剩 1.5%），已弃用。
- 人物层：alpha 硬化（CUTOFF=40）去掉若有若无的淡边，原画实心轮廓光不受影响。
- **幂等**：人物层每次从 `L2_raw.png` 重新裁 bbox 再清理，
  卡框每次从 `*_soft.png` 备份重算，重复运行不会累积硬化。

结果：卡框淡边 5.4% → **1.7%**，实心线描保持 6.7%；人物层半透明降到约 1.3%。

## 14. 像素点对点诊断（2026-11-16）

用户问「是不是卡牌像素缩放后不点对点造成的糊化」——**判断成立**，
但要分清哪一层该讲点对点、哪一层不该。

### 三层缩放比（实测）

| 层 | 源图 | 显示 | 倍率 | 是否该点对点 |
|---|---|---|---|---|
| **边框** `frame_*.png` | 406×522 | 203×261 | **正好 2:1** | **应该**，且本可完美 |
| L1 背景 | 1806×2322 / 896×1152 | 199×257（含 10px 视差余量） | 9.0x / 4.5x 缩小 | 不该，高清插画缩小靠降采样 |
| L2 人物 | 1077×1519 等 | 194×274（`CharScale=1.05` → h=274.05） | 5.5x 缩小 | 不该 |

### 三个根因

**① 边框该 2:1 点对点，却用了线性插值。**
`CardBorderFactory.CreateNode` 原设 `LinearWithMipmaps`。
离线量化同样 406×522 → 203×261 的半透明软边占比：

| 采样 | 软边占比 |
|---|---|
| Nearest | **1.43%** |
| Bilinear | 16.97% |
| Lanczos | 15.78% |
| BOX / mipmap | 13.38% |

线性插值把 1px 金线洗成 2~3px 软边，是 Nearest 的近 10 倍。

**② `mipmaps/generate=false`，`LinearWithMipmaps` 名不副实。**
所有 `.png.import` 都关了 mipmap 生成，所以该过滤标志取不到 mip 层，
实际退化成纯 Linear —— 只有插值糊化，没有 mipmap 的抗抖动收益。
（反过来：L1 缩 9 倍其实**需要** mipmap 防噪点抖动，那层却也没有。）

**③ 仇恨缩放让尺寸和位置都变成非整数。**
`HeroCardLayer.ScaleOf` 给卡 0.93~1.08 的缩放，`BuildOne` 直接
`size = baseSize * scale`、`position = cell + (baseSize-size)*0.5f`，
两者都带小数 → 纹理落在半像素上，每帧被重采样，边缘持续发虚。
这层才是"不点对点"最字面的来源，且上轮「边缘毛糙」只查了抠像残留、漏了它。

### 改动（2 处）

- `CardBorderFactory.CreateNode`：`LinearWithMipmaps` → **`Nearest`**
- `HeroCardLayer.BuildOne`：size 与 position 用 `Mathf.Round` **吸附整数像素**

人物/背景的 `LinearWithMipmaps` **保持不变**：它们是 4.5~9x 缩小的高清插画，
改 Nearest 会产生锯齿噪点；且视差本身是连续浮点（ `_tilt.Lerp` + `ShiftPx*Depth`），
强行取整会让视差变成 1px 台阶跳动，得不偿失。

### 验证

实机 sRGB 帧同位置 3 倍放大对比 `preview/compare_card_snap.png`：
金线回纹更锐利、粉色外沿更利落，无断线/缺口。
量化（卡框区域）：高梯度像素 17060 → **17702**、平均梯度 74.1 → **79.1**、
暖色线条像素 9875 → **10093**（不减反增，证明没丢线）。

### 局限与可选彻底方案

- **完全点对点要求所有卡同尺寸**。整数吸附后 `scale≠1.0` 的卡仍是
  406→219 之类的非整数缩小（1.85x），只能保证硬边、不能保证均匀像素。
  若要彻底解决，需取消仇恨**尺寸**缩放，改用发光/描边表达仇恨，
  让所有卡固定 203×261 —— 这会改变玩法表现，需另行确认。
- **窗口画布**：`window/stretch/scale_mode = "fractional"`。当前窗口正好
  1920×1080，`content_scale_factor = 1.0` 无影响；但窗口改成非该尺寸时，
  整个 canvas 会做非整数缩放，所有 UI 一起糊。
  可设 `scale_mode = "integer"` 让缩放吸附整数倍，代价是非整数倍窗口留黑边。

## 16. 人物破框部分虚化（2026-11-16）

用户：「感觉人物突出边框部分有虚化现象」。

### 根因：渐隐 shader 是"裁剪之前"的设计，已经过时

`CardArtFx.FadeShader()` 给人物溢出层 `_charOver` 的**四边**各做
`edge_fade = 0.05`（占 UV 边长 5%）的 alpha 渐隐，原意是藏住
"素材被裁切后四边的硬切线"（见文件头 2026-11-14 注释）。

但之后 `CropPortraits.py` 已把 L2 **裁到 alpha 边界** —— 四边本来就是
自然透明的人物轮廓，根本不需要再靠渐隐藏切线。这个 shader 剩下的唯一作用
就是把破框的头发洗虚。

### 量化（沈孤鸿 L2 446×944，显示 129.5×274）

| 项 | 值 |
|---|---|
| 顶部渐隐带 | 5% × 274 = **13.7px**（显示尺寸） |
| 横向渐隐带 | 5% × 129.5 = **6.5px** |
| 顶部 2% 处的 alpha 系数 | **0.326**（发梢被淡掉约 2/3） |
| 顶部 5% 带内实心像素 | 2218 个全被削弱，最外一行归零 |

破出卡框的头顶 / 发髻 / 飘带正好落在顶部这条带里 → 发灰、半透明、
溶进暗背景。卡内脸部不在带内，所以形成"破框部分比卡内糊"的反差。

### 改动（`CardArtFx.cs`，一处影响三处调用）

渐隐收敛为**只作用底边**：
```glsl
float d = 1.0 - UV.y;
float a = smoothstep(0.0, bottom_fade, d);
```
`EdgeFade = 0.05` → `BottomFade = 0.02`（约 5.5px，只用来柔化被信息带
硬切的那条底边）。**顶部与左右完全不淡**。

`MakeCharOverlay` 的三处调用（战斗卡 / 卡册卡 / 详情大卡）共用这份 shader，
改一处全部受益，无需逐个改。裁剪后轮廓是自然透明边，去掉渐隐不会露硬切线。

### 一次实测无效、主动回退的探索

曾怀疑第二来源是 `_charOver` 的浮点尺寸/位置（`w=129.5`、`h=274.05`、
`_charBase` 带小数、视差 `charOff` 连续浮点）导致半像素重采样，于是做了两步：

| 改动 | 实测 | 处理 |
|---|---|---|
| `LayoutCharOver` 尺寸与基准位置 `Mathf.Round` | 静态对齐，无副作用 | **保留** |
| `Animate` 每帧把 `Position` 取整 | 破框区边缘方差 4573.6 → **4544.4**（无改善），且会让 ±4.4px 慢速视差变成 1px 台阶跳动 | **回退** |

视差 `ShiftPx=8 × Depth[1]=0.55 ≈ 4.4px`，连续浮点在这里比台阶更划算。
**判据：无收益就不引入风险**，探索性改动不因为"写好了"而保留。

### 验证

编译 0 错 0 警；实机 sRGB 帧对比 `preview/compare_char_final.png`：
右侧发髻为清晰深色实块、发丝分明，左侧发灰半透明；卡内脸部一致、无硬切线。

像素差分确认改动范围精确：破框头顶区变化像素 2.46%，
**卡内脸部 0.00%、卡内背景 0.00%**（`preview/compare_char_snap.png` 为整数吸附探索的对照，已作废）。

### 若仍觉得边缘偏软

`_charOver` 用 `LinearWithMipmaps`（§15 开启 mipmap 后生效），
L2 缩小约 3.4x 会混合 mip 层，半透明发丝有正常抗锯齿软化。
这是消除混叠的代价，不是缺陷；再要更硬需离线预降采样 L2 到 2x 显示尺寸，
改动面较大，本次未做。

## 21. 大卡人物破框收敛（2026-11-16）

用户：「大卡人物突出太多了」。

### 量化

| 界面 | 卡高 | 旧 `CharScale` | 人物高 | 顶部探出 |
|---|---|---|---|---|
| 战斗卡 | 261 | 1.05 | 274 | **13px**（合理） |
| 卡册大卡 | 739 | 1.10 | 813 | **74px** |
| 详情大卡 | 604 | 1.11 | 670 | **66px** |

大卡探出量是战斗卡的 5 倍多，头发顶到标题区、把"卡册 · 沈孤鸿"几个字都遮了。

### 根因：第四次"裁剪前提失效"

两处大卡的注释写得一模一样：
> "按可见探出 ~14px 反推（**素材透明留白均值约 9%**）"

`CropPortraits.py` 把 L2 裁到 alpha 边界后，**这 9% 留白没了**。
原来 1.10 的 74px 里约 66px 是透明留白、只有 8px 是真人物；
裁剪后 74px 全部变成实打实的人物破框。倍数没变，观感翻了近十倍。

### 改动：倍数 → 绝对像素

`GalleryCard` / `UnitDetailView` 各加
```csharp
const float CharOverhang = 16f;   // 人物头顶探出卡框的绝对像素
```
`h = 卡高 + CharOverhang`（原来是 `卡高 * CharScale`），底边仍对齐卡底。
绝对像素不受卡高与素材留白比例影响，也不会再随"素材是否带留白"漂移。
与战斗卡的 13px 同量级，三处统一。

### 验证

编译 0 错 0 警；实机 sRGB 帧：
- `preview/compare_overhang.png`：卡册从 74px → 16px，头顶不再遮标题，
  人物仍头到脚完整、脸部清晰，保留适度破框立体感
- `preview/over_detail.png`：详情大卡头发不再顶到标题区，与卡册一致
- 战斗卡未改动（13px 本来就合适）

### `CropPortraits.py` 后的假设复核清单

今天连续四次踩同一个前提（L2 裁到 alpha 边界），逐条列出以免再漏：

| # | 失效的旧假设 | 修正章节 |
|---|---|---|
| 1 | "四边有硬切线，要渐隐藏住" → 四边本就是自然透明轮廓，渐隐只把破框头发洗虚 | §16 |
| 2 | "L2 固定 7:9" → 宽高比 0.46~0.58 各异，`KeepAspectCovered` 会切头 | §19 |
| 3 | "L4 每个条目各一份" → 62 份逐像素相同，合并共享（现已完全弃用） | §18 / §20 |
| 4 | "素材留白 9%，CharScale 1.10 只探出 14px" → 留白没了，实探 74px | §21 |

**判据：凡是注释里出现"按素材留白 / 固定比例 / 每张各一份"这类前提，
都要回头确认 `CropPortraits.py` 之后它还成不成立。**
